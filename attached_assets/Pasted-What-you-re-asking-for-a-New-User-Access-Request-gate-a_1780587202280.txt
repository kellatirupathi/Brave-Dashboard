What you're asking for: a "New User Access Request" gate + admin approval
A. New-user (student) side — the gate
When someone logs in via the SSO form link, check whether their ID exists in the roster:

In roster → no check, go straight to Get Started as today (existing flow, untouched).
Already an existing user → no check, normal flow (untouched).
NOT in roster (brand-new SSO user) → freeze the app: hide Leaderboard, Get Started, and Resources. Show only one form with these fields:
Full name
NIAT ID
Email
Campus (dropdown)
Mobile number
Section name
One Submit button → saves the data into a separate table.
After submit → the form is replaced by a message like "You've submitted your request. Please wait until admin approval." They can't use the app until approved.
B. Admin side — review & decide
New sidebar item "New Users" under the Setup submenu → route /admin/new-users-requests.
Page layout:
Top-left: "New requests" title.
Top-right: search box, status dropdown (All / Approved / Rejected), Export button, Add button.
Body: row-wise cards, each a compact 2-line summary of the candidate.
Each card (right side): View, Approve, Reject.
View → opens a detail page for just that candidate (full submitted details).
Approve → candidate's data is written to both the roster and users tables → their Leaderboard / Get Started / Resources unfreeze (they get normal access).
Reject → they stay frozen and just see a "rejected" status; can't do anything.
C. Reversible decisions + badges
After a decision, the card shows an Approved or Rejected badge on the right.
On the detail (View) page:
If currently Approved → show a Reject button at the bottom (admin can reverse to rejected anytime).
If currently Rejected → show an Approve button (admin can reverse to approved anytime).
So the admin can flip the decision from the detail page at any time.
Important: much of this scaffolding already exists
There's already an access_requests table (fullName, email, batch, niatId, campusName, status, notes).
Admin endpoints already exist: GET /admin/access-requests and PATCH /admin/access-requests/:id (admin.ts:1781).
There's a not-on-roster.tsx page (the current "you're not on the roster" screen).
The roster gate in App.tsx is currently DISABLED (commented out) — your feature re-enables a version of it but routes non-roster users to the form instead of a dead-end.
So this is largely extending the existing access-request flow, not building from zero.
