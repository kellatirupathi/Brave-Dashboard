Why it's safe (the engineering case)
Concern	Why it's fine
Will it break the existing app?	No. The cron script is a new isolated file in scripts/. The existing api-server, frontend, schema, and business logic are not touched. The app keeps running while sync happens.
Will it slow down prod?	Minimal. The sync reads each table once at 2 AM IST (lowest traffic). At 54 MB total, the full read takes ~30 seconds. Postgres handles this without breaking a sweat.
Will it lock tables?	No — SELECT doesn't lock writes in Postgres. Students submitting journals during sync won't see any delay.
Will it conflict with existing crons?	No. You already have cron-overdue-notifications.ts and cron-reminders.ts. Adding one more cron is the same pattern.
Schema mismatch risk?	Zero — the script reads your live Drizzle schema and creates identical Supabase tables. They'll always match because they come from the same source code.
What if Supabase is down?	Sync fails silently, logs an error, retries next cycle. Prod is unaffected.
What if cron crashes mid-sync?	Full-overwrite mode means partial state in Supabase. Next run wipes and redoes it. No corruption possible on Replit side.
Real risks I won't hide from you
