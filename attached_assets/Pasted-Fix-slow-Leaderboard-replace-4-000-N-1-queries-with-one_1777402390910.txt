Fix slow Leaderboard — replace ~4,000 N+1 queries with one aggregate SQL query (scales to lakhs of rows)
/leaderboard (used by Admin, Coordinator, and Student leaderboard pages) is slow because the route fires 4 separate queries per team × ~991 active teams ≈ 4,000 round-trips per request (leaderboard.ts:44-83). Search adds another 4–6 queries. Even when the UI shows only the top 10, the route still pulls every team and slices in JS.

Refactor to a single aggregate query, paginate at the database, fold search into the same query, add the missing indices, and harden the path so it stays fast at lakh-scale data. Expected wall-clock: seconds → <150 ms today, <300 ms at 1 lakh teams / 5 lakh revenue entries.

1. Backend — artifacts/api-server/src/routes/leaderboard.ts
Replace the entire body of GET /leaderboard with a single SQL query that joins teams, campuses, and pre-aggregated revenue / order book / project subqueries. No for loop, no Promise.all over teams, no per-team db.select.

1.1 Query shape

SELECT
  t.id              AS team_id,
  t.name            AS team_name,
  t.tagline,
  t.photo_url,
  t.is_featured,
  t.is_hidden,
  t.campus_id,
  c.name            AS campus_name,
  COALESCE(r.total, 0)        AS total_revenue,
  r.last_payment              AS last_payment_date,
  COALESCE(o.total, 0)        AS total_order_book,
  COALESCE(p.active_count, 0) AS active_projects,
  ROW_NUMBER() OVER (
    ORDER BY t.is_featured DESC, COALESCE(r.total, 0) DESC, t.id ASC
  ) AS rank
FROM teams t
LEFT JOIN campuses c ON c.id = t.campus_id
LEFT JOIN (
  SELECT team_id, SUM(verified_amount) AS total, MAX(payment_date) AS last_payment
  FROM revenue_entries WHERE status = 'verified' GROUP BY team_id
) r ON r.team_id = t.id
LEFT JOIN (
  SELECT team_id, SUM(verified_amount) AS total
  FROM order_book_entries WHERE status = 'verified' GROUP BY team_id
) o ON o.team_id = t.id
LEFT JOIN (
  SELECT team_id, COUNT(*) AS active_count
  FROM projects WHERE status = 'active' GROUP BY team_id
) p ON p.team_id = t.id
WHERE t.status = 'active'
  AND (CAST($1 AS int) IS NULL OR t.campus_id = $1)
  AND (CAST($5 AS boolean) IS TRUE OR t.is_hidden = false)
  AND (
    $2::text IS NULL OR
    t.name   ILIKE '%' || $2 || '%' OR
    c.name   ILIKE '%' || $2 || '%' OR
    EXISTS (
      SELECT 1
      FROM team_members tm
      JOIN users u ON u.id = tm.user_id
      LEFT JOIN roster ro ON (ro.email = u.email OR ro.student_id = u.forms_user_id)
      WHERE tm.team_id = t.id
        AND (
          (u.first_name || ' ' || u.last_name) ILIKE '%' || $2 || '%' OR
          u.email      ILIKE '%' || $2 || '%' OR
          ro.niat_id   ILIKE '%' || $2 || '%'
        )
    )
  )
ORDER BY rank
LIMIT $3 OFFSET $4;
Plus a count(*) query with the same WHERE for pagination metadata. Run both in Promise.all.

Build the query with Drizzle's sql tagged template (or db.execute(sql\...`)`) so parameters are properly bound. Do not string-concatenate user input.

1.2 Handler logic
Parse view (national | campus | top10), campusId, search, page, pageSize. Defaults: page=1, pageSize=50. Cap pageSize server-side at 100 to protect the API.
If view === "campus" and no campusId, fall back to req.user.campusId.
If view === "top10", force pageSize=10, page=1.
Pass $5 = (req.user.role === "admin") so admins see hidden teams and others don't (this also closes the existing audit bug where coordinators saw hidden teams).
Compute isDemoEligible in JS from the returned total_revenue and programmeConfig.demoEligibilityThreshold.
clientCount is currently always 0 — leave as-is.
Return:

{ items, total, page, pageSize }
Items shape stays compatible: teamId, teamName, campusName, campusId, tagline, photoUrl, totalRevenue, totalOrderBook, activeProjects, clientCount, lastPaymentDate, isDemoEligible, isFeatured, isHidden, rank.

Delete the per-team Promise.all block (lines 45–83), the search-augmentation block (lines 90–146), and the JS sort + slice(0, 10) (lines 150–157). All of that is now in SQL.

2. Database indices + extension — new migration in lib/db/migrations/
Idempotent, safe to re-run:


CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX IF NOT EXISTS idx_revenue_entries_team_status ON revenue_entries (team_id, status);
CREATE INDEX IF NOT EXISTS idx_order_book_team_status     ON order_book_entries (team_id, status);
CREATE INDEX IF NOT EXISTS idx_projects_team_status        ON projects (team_id, status);
CREATE INDEX IF NOT EXISTS idx_teams_status                ON teams (status);
CREATE INDEX IF NOT EXISTS idx_team_members_team           ON team_members (team_id);
CREATE INDEX IF NOT EXISTS idx_team_members_user           ON team_members (user_id);

CREATE INDEX IF NOT EXISTS idx_users_name_trgm
  ON users USING gin ((first_name || ' ' || last_name) gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_users_email_trgm
  ON users USING gin (email gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_roster_niat_trgm
  ON roster USING gin (niat_id gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_teams_name_trgm
  ON teams USING gin (name gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_campuses_name_trgm
  ON campuses USING gin (name gin_trgm_ops);
The trigram indices are what keep ILIKE '%term%' fast at lakh-scale data. Without them, search degrades linearly with row count.

Run via pnpm --filter @workspace/db run push (or generate a migration file if the project uses migration files).

Wrap the handler in a tiny TTL cache keyed by (view, campusId, search, page, pageSize, isAdmin, leaderboardVersion) with 30 s TTL. Use a Map with timestamp cleanup (or lru-cache if already in deps).


const cache = new Map<string, { at: number; payload: unknown }>();
const TTL = 30_000;
let leaderboardVersion = 0;
export const bumpLeaderboardVersion = () => { leaderboardVersion++; };
Skip cache when search is non-empty to avoid leaking results across users.

Bump leaderboardVersion (which busts the cache) from inside:

Revenue verify / unverify / reject (routes/financials.ts)
Team approve / reject / delete
Order book verify
Team rename / hide / feature toggle
That makes repeat leaderboard hits sub-millisecond between mutations.

6. Scale-readiness checklist (so it stays fast at lakhs of rows)
Concern	Hardening done in this PR
4,000 N+1 round-trips per request	✅ replaced with 1–2 queries
ILIKE '%term%' linear scans on big tables	✅ trigram indices on users.name, users.email, roster.niat_id, teams.name, campuses.name
OFFSET slowness at deep pages	⚠️ acceptable today; if leaderboard ever needs page 1000+ at lakh scale, switch to keyset pagination (WHERE (total_revenue, id) < (lastTotal, lastId)). Not needed yet — note in code comment.
Repeated full aggregation on every keystroke	✅ 30s in-memory cache (skipped when searching)
pageSize abuse	✅ capped at 100 server-side
Hidden teams visible to non-admins	✅ filter applied in SQL WHERE, not JS
Materialized stats table for crore-scale	🕒 not needed yet — add later as team_stats MATERIALIZED VIEW refreshed on revenue mutations only if traffic genuinely outgrows the index path
For BRAVE's actual current and near-future scale (≤ 50K teams, ≤ 5 lakh revenue entries), this fix is sufficient and the page will stay under 300 ms.
