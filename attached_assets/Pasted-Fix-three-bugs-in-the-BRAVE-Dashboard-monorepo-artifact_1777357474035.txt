Fix three bugs in the BRAVE Dashboard monorepo (artifacts/api-server, artifacts/brave-dashboard, lib/db). Keep diffs minimal, no unrelated refactors.

────────────────────────────────────────────────
BUG 1 — "Invite a teammate" must search the ROSTER table only, and a successful invite must be stored against the invited student
────────────────────────────────────────────────

Server file: artifacts/api-server/src/routes/team-flow.ts
  - GET /students/search (around line 201) — search source is correct (rosterTable, scoped by inviter's campusId). Two changes:
      a) Widen the WHERE: in addition to fullName and niatId, also OR-match `email` and `studentId` (ilike %q%). The placeholder text already promises "name, email, NIAT ID or student ID".
      b) Keep the existing `eq(rosterTable.campusId, req.user.campusId)` and `isWhitelisted = true` filters — do NOT join or search against the users table for matching. The users table is only used afterwards to attach userId/onTeam metadata for display.
  - POST /teams/:id/invitations (the send-invitation handler) — the invite must be persisted against the invited student so it shows up in their /get-started "pending invitations" list immediately:
      a) Accept either { inviteeId } (existing user) OR { rosterId } (roster row with no user account yet).
      b) If only rosterId is given and no user row exists yet, insert a placeholder users row keyed by the roster's email/formsUserId with role='student' and campusId = roster.campusId, then create the invitation pointing at that user.
      c) Reject if inviter and invitee campuses differ, if invitee is already on a team, or if a pending invitation/join-request already exists between them.
      d) Always insert into team_invitations with status='pending', inviterId, inviteeId, teamId, createdAt, expiresAt = now + 90 days.
      e) Insert a notifications row for the invitee ("You have been invited to join <team>").

Frontend: artifacts/brave-dashboard/src/pages/student/team.tsx (invite dialog)
  - Pass rosterId when the matched roster row has no linked user account yet, otherwise pass inviteeId.
  - On mutation success, invalidate: my-team invitations, pending-invitations, students/search, and the invitee's notifications cache key.

Acceptance: searching "ram" / "ram@..." / "NIAT123" / a studentId all return the same person if any field matches; only same-campus, whitelisted, not-on-a-team rows appear; sending an invite immediately shows up under the invited student's /get-started Pending Invitations.

BUG 2 — Joining by invite code returns 403 "This team belongs to a different campus" for SAME-CAMPUS students (see screenshot: code D2XCP2MZ, student Ram Charan)
────────────────────────────────────────────────

Server file: artifacts/api-server/src/routes/team-flow.ts → POST /teams/join-by-code (around line 256-284)
Current check (line 269): `if (!req.user.campusId || team.campusId !== req.user.campusId) → 403 "different campus"`. This is firing for legitimate same-campus students.

Root cause is one or more of:
  (a) req.user.campusId is null because the joining student is auto-provisioned via SSO and never had their campusId backfilled from the roster.
  (b) team.campusId was not set when the team was created, so it's null/0, and the strict equality fails.
  (c) The roster row for the joining student exists but the user row's campusId is stale.

Fix:
  1. At the very start of the handler, if req.user.campusId is null, look up the joining user's roster row by email or formsUserId (the same lookup pattern used in /students/search). If a whitelisted roster row exists, UPDATE users.campusId = roster.campusId for this user and continue with the resolved value. If no roster row exists, return 403 with a SPECIFIC error: "Your account is not on the campus roster. Contact your coordinator." — never the generic "different campus" message.
  2. Validate at team creation that team.campusId is NOT NULL — if it is, return 500 with a logged warning. Backfill any existing teams whose campusId is null using the leader's campusId (one-time SQL or a startup migration).
  3. The campus comparison must be: `Number(team.campusId) === Number(joiningUser.campusId)` and both must be truthy. Return distinct, accurate errors:
        - 404 "Invite code not found" when no team matches the code
        - 400 "You are already on a team" when getMembership returns a row
        - 403 "This team is in a different campus" ONLY when both campusIds are present and genuinely differ
        - 403 "Your account is not on the campus roster..." when the joiner has no campusId AND no roster match
  4. Normalize the code on both sides: `code.trim().toUpperCase()` server-side (already done) AND on the frontend before submit — so D2XCP2MZ vs d2xcp2mz vs " D2XCP2MZ " all succeed.
  5. On success: insert into team_members, cancel other pending invitations/join-requests for this user (cancelOtherPendingForUser is already called — keep it), insert a notification for team leader, and return the joined team object (so the client can route straight to /team without a second fetch).

Frontend: artifacts/brave-dashboard/src/pages/student/get-started.tsx (Join by code dialog)
  - Trim+uppercase the code before submit.
  - Surface the server's specific error string in the toast (don't replace it with a generic message).
  - On success, invalidate the same query keys as Bug 3 below and route to /team.

Add a regression test that creates two teams in the same campus, has a same-campus student join the second team's code, and asserts 200 + team_members row inserted. Add a second test for a roster student whose user row has campusId=null — assert that join succeeds and the user row's campusId is filled in from the roster.

BUG 3 — After creating a team, the rest of the app stays stale until full logout + login
────────────────────────────────────────────────

Where: artifacts/brave-dashboard/src/pages/student/get-started.tsx (create-team mutation), the same pattern likely repeats in any "membership-changing" mutation (accept invitation, approve join request, leave team, join-by-code, team approval). Sidebar role/team badge, /team, /, /projects, /leaderboard, /notifications, and useAuth all read cached data that is not invalidated.

Fix:
  1. In the create-team mutation's onSuccess (and on join-by-code success, accept-invitation success, leave-team success, approve-join-request success):
       - Call queryClient.invalidateQueries() for ALL of these keys (grep the codebase to find their exact tuples; do not hardcode strings that don't exist):
            ['auth', 'user']  // useAuth
            ['my-team']
            ['team-members']
            ['team', teamId]
            ['invitations', 'mine']
            ['join-requests', 'mine']
            ['leave-requests', 'mine']
            ['dashboard']
            ['notifications']
            ['projects']
            ['leaderboard']
       - Then setLocation('/team'). Do NOT use window.location.reload() or window.location.href — the SPA must update in place.
  2. If useAuth caches the user object via React Query, ensure its query is part of the invalidation set so role/team membership refreshes without re-login. If it is in a custom context, add a refetch() call alongside the invalidations.
  3. Verify that the query keys used by sidebar (role/team chip), /team page, dashboard cards, and leaderboard are ALL keys that get invalidated. If any page uses a non-React-Query store (Zustand/local state) for "current team", reset it explicitly in the same onSuccess handler.
  4. Add a small util `invalidateMembershipQueries(queryClient)` in artifacts/brave-dashboard/src/lib/queries.ts so all five mutations call the same function — single source of truth.

Acceptance: create a team, observe /team, sidebar, /, and /leaderboard all reflect the new team within one network round-trip, no full reload, no re-login.
